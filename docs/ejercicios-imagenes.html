Imágenes del catálogo de ejercicios

El catálogo conserva su arquitectura Controller → Service → Repository y sus permisos ADMIN. No se modifica la autenticación ni los otros módulos.

Datos nuevos

Ejercicios y EjerciciosDTO incorporan imagenUrl, imagenAutor, imagenLicencia e imagenLicenciaUrl. Son opcionales. Las URLs utilizan HTTPS sin credenciales ni fragmentos, hasta 2048 caracteres; los créditos admiten 255.

Un PUT antiguo que omite imagenUrl conserva la foto existente. Un PUT con imagenUrl nula o vacía retira la foto y sus créditos. El servidor guarda la URL; no descarga ficheros arbitrarios.

Instalación

  1. Respaldar la base y ejecutar ejercicios-imagenes.sql con una cuenta propietaria. La cuenta de consulta de pgAdmin no sirve para alterar tablas.
  2. Compilar y desplegar el backend; después publicar el frontend compatible.
  3. En ADMIN → Catálogo de ejercicios → Editar, introducir el enlace directo de una fotografía autorizada y sus créditos. Revisar que corresponde al ejercicio, comprobar la vista previa y guardar.

Importación de imágenes desde wger

ADMIN puede pulsar Sincronizar con wger en el catálogo. Utiliza el endpoint existente POST /ejercicios/wger/sincronizar, protegido para ADMIN. Importa ejercicios nuevos, actualiza sus textos y completa las imágenes ausentes por el ID exacto WgerId. No asigna fotos por parecido de nombres o grupo muscular, no elimina ejercicios y conserva las imágenes existentes, incluidas las elegidas manualmente.

Se admiten fotografías e ilustraciones. La etiqueta style=Photo no garantiza que una imagen sea una fotografía; por eso la interfaz utiliza el término «Imagen». Se prefiere la imagen principal válida de cada ejercicio. Se omiten recursos marcados como generados por IA, de otro ID, con URL insegura o sin licencia abierta identificada. Solo se guardan URLs HTTPS de medios de wger y los créditos propios de la imagen. Las licencias se consultan una sola vez por sincronización; no se confunden con la licencia del texto.

El resultado mantiene los contadores existentes y añade imagenesImportadas. HTTP 206 indica sincronización parcial: si fallan las licencias, los ejercicios se conservan y el usuario puede reintentar. Una sincronización repetida no vuelve a contar las imágenes ya guardadas. No garantiza cobertura total: ejercicios sin imágenes disponibles conservan su estado pendiente.

Si una imagen se elimina manualmente, una sincronización posterior puede volver a completarla. Para sustituirla, ADMIN guarda la URL nueva y sus créditos. No se descargan archivos arbitrarios en el servidor. El navegador carga las imágenes cuando las necesita y permite ampliarlas en un diálogo.

Frontend

El componente standalone compartido fotoejerciciocomponent presenta imagen, créditos, visor y estados pendiente/error. Se reutiliza en ADMIN, el formulario de edición y el catálogo de Cliente. El catálogo de Cliente mantiene la tabla existente mediante el selector Tarjetas / Lista, además de sus filtros y paginación.

Despliegue y prueba

  1. Aplicar las cuatro columnas opcionales del SQL con una cuenta propietaria y desplegar el backend actualizado. En local, si ya se utiliza ddl-auto=update, Hibernate puede crear estas columnas al reiniciar; no se modifica esa configuración.
  2. Desplegar el frontend compatible e iniciar sesión como ADMIN.
  3. Abrir el catálogo, pulsar Sincronizar con wger y revisar los contadores. La operación también actualiza los textos de ejercicios importados, como hacía antes.
  4. Comprobar una imagen importada, un ejercicio sin imagen, la edición manual y que Cliente puede consultar pero no sincronizar.

Las pruebas automatizadas usan H2 y respuestas simuladas de wger. No importan registros en PostgreSQL local ni Render. La ejecución real sobre una base se realiza desde el botón ADMIN cuando el backend y el esquema estén actualizados.

Fuentes: API oficial de wger; definición oficial de estilos y marca de IA.
